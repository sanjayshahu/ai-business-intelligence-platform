# Phase 0 — Task 0.3: First-Slice Contract — Pure Batch Material Cost

Status: Written specification. No code, no project generation in this task.
Depends on: Task 0.2 (D-0.2-1, D-0.2-2, D-0.2-3, D-0.2-9).
Implemented by: Task 0.4.
Governing spec: Master Prompt §11, §13, §14, §43, §51, §52, §67, §75, §76.

---

## 1. Objective

Define, in writing, the smallest valuable vertical slice of the platform:
a framework-independent, deterministic calculation of

    total batch material cost
    and cost per produced unit

for a single production batch composed of materials with quantities and unit prices.

This is the first product code that will exist. Its contract is fixed here so that
the implementation in Task 0.4 cannot drift.

---

## 2. Business reason

The platform's core promise is "know your true cost." Before any persistence, API,
UI, or AI exists, the calculation must be correct, explicit, and testable. This slice
establishes the rule that financial results come from deterministic code, never from
an LLM (Master Prompt §5).

---

## 3. Explicit scope boundary

In scope:
- One batch, one currency.
- A list of materials, each with quantity, unit of measure, unit price.
- A produced-units count for the batch.
- Total batch material cost.
- Cost per produced unit.

Out of scope (deliberately, and per Master Prompt §14, §18):
- Yield, waste, scrap, rework.
- Saleable quantity (Phase 8).
- Pricing, margin, markup (Phase 10).
- Profitability (Phase 11).
- Labor, energy, packaging, overhead.
- Multi-currency conversion.
- Effective-dated prices.
- Persistence, API, UI, tenancy, AI.

The first slice answers exactly one question:
> Given these materials and this batch, what did the material cost?

---

## 4. Domain model

### Value objects

`Money`
- `amount`: decimal-safe value
- `currency`: ISO 4217 string (single currency per batch in this slice)

`Quantity`
- `value`: decimal-safe value
- `unit`: unit-of-measure code

`UnitPrice`
- `amount`: decimal-safe value
- `currency`: ISO 4217 string
- `perUnit`: unit-of-measure code (must match the quantity's unit within a line)

`MaterialLine`
- `materialId`: string
- `quantity`: `Quantity`
- `unitPrice`: `UnitPrice`

`BatchInput`
- `materials`: `MaterialLine[]` (at least one)
- `producedUnits`: integer > 0
- `currency`: ISO 4217 string

### Result

`BatchCostResult`
- `totalBatchCost`: `Money`
- `costPerProducedUnit`: `Money`
- `producedUnits`: integer
- `currency`: string
- `calculationVersion`: string (e.g. `"batch-cost-v1"`)
- `assumptions`: string[] (see §7)
- `lineCosts`: `{ materialId, lineCost: Money }[]`

---

## 5. Business rules

BR-1. Every `MaterialLine` must have `quantity.value >= 0` and `unitPrice.amount >= 0`.
BR-2. `quantity.unit` must equal `unitPrice.perUnit` within a line.
BR-3. All lines must share the same `currency` as `BatchInput.currency`.
BR-4. `producedUnits` must be an integer > 0.
BR-5. `materials` must be non-empty.
BR-6. `lineCost = quantity.value × unitPrice.amount`, computed with decimal-safe arithmetic.
BR-7. `totalBatchCost = Σ lineCost`, in the batch currency.
BR-8. `costPerProducedUnit = totalBatchCost ÷ producedUnits`, rounded by the rule in §6.
BR-9. Rounding is applied once, at the boundary of the result. Intermediate
      calculations are not rounded.
BR-10. No floating-point arithmetic is used for money.

---

## 6. Arithmetic and rounding

- All money and quantity math uses a decimal-safe representation.
  Choice of library is left to Task 0.4 (e.g. `decimal.js`, `big.js`, or a minimal
  fixed-point integer-micros implementation).
- Intermediate line costs are carried at full precision.
- Final outputs are rounded using `half-up` to 4 decimal places for money in this slice.
  (Currency-specific minor-unit rules are out of scope; ISO minor units will be
  introduced together with real pricing in Phase 10.)
- `totalBatchCost` and `costPerProducedUnit` are the only rounded values exposed.
- Rounding is deterministic and covered by tests (§9).

---

## 7. Assumptions echoed in the result

The result echoes a fixed, ordered list of assumptions so downstream consumers
and later AI explanations can cite them (Master Prompt §35, §66):

- `"currency: single currency per batch"` (from `BatchInput.currency`)
- `"rounding: half-up, 4 dp"` 
- `"yield: not modelled (cost is per produced unit, not per saleable unit)"`
- `"pricing: not modelled"`
- `"overheads: not modelled"`

This list is part of the contract and is versioned via `calculationVersion`.

---

## 8. Rejection rules

The calculation must reject, with a typed error, any of:

- `materials` empty or not an array.
- `quantity.value < 0` or `unitPrice.amount < 0`.
- `quantity.unit !== unitPrice.perUnit` within a line.
- Line currency !== batch currency.
- `producedUnits` not a positive integer.
- Unknown or missing currency code.

Errors must be typed (not bare `Error`), must not leak stack traces, and must
identify the offending field and line where applicable (Master Prompt §67).

---

## 9. Test cases (minimum)

Unit tests, framework-independent, no React/DOM:

1. Single material, integer quantity, integer price → exact expected total.
2. Multiple materials → sum is exact; per-unit division is exact when divisible.
3. Multiple materials → per-unit value that requires rounding; assert the exact
   rounded value and that no rounding occurred before the final division.
4. `quantity.value = 0` → allowed; line cost 0; result still valid.
5. `unitPrice.amount = 0` → allowed; line cost 0.
6. Negative quantity → rejected with a typed error.
7. Negative price → rejected with a typed error.
8. Unit mismatch within a line → rejected.
9. Currency mismatch between line and batch → rejected.
10. `producedUnits = 0` → rejected.
11. `producedUnits` non-integer → rejected.
12. `materials = []` → rejected.
13. Rounding boundary: a value exactly halfway at the 4th decimal → `half-up` applied.
14. Large batch (many lines) → sum deterministic and order-independent.

Test invariants (Master Prompt §52):

- Sum of `lineCosts` equals `totalBatchCost` after rounding only at the boundary.
- Result is order-independent with respect to input material order.
- Same inputs, same `calculationVersion` → identical output (determinism).

---

## 10. Failure behavior

- All rejections from §8 are typed domain errors.
- No partial results are returned on rejection (Master Prompt §47, §67).
- No numeric result is fabricated or defaulted.

## 12. Database / API / frontend / AI changes

None in this slice. This is a pure domain library.

---

## 13. Security

No security surface in this slice. Domain library has no I/O, no auth, no tenancy.
Failures must not leak internal state.

---

## 14. Performance

Not a concern at this slice. Must be O(n) in the number of material lines.
No premature optimization.

---

## 15. Observability

None required. The result carries `calculationVersion` and `assumptions`, which is
sufficient traceability for this slice (Master Prompt §35, §65).
