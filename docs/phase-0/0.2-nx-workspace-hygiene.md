## 3. Decisions

### D-0.2-1 — Library location
Product libraries live under `libs/`, not `packages/`.
`packages/` remains reserved for future publishable packages. Nothing is planned for it now.

### D-0.2-2 — Library resolution
Resolve libraries via npm workspace glob + package `exports`, NOT via `tsconfig` `paths`.
When the first library is created:
- add `"libs/*"` to root `package.json` `workspaces`,
- give the library a package name matching its Nx project name,
- do NOT add a `paths` alias in `tsconfig.base.json`.

### D-0.2-3 — Tag scheme
Tag projects on two axes:
- `type:*` — `domain`, `application`, `infrastructure`, `ui`, `util`, `e2e`, `app`.
- `scope:*` — bounded context (`costing`, `pricing`, `profitability`, `variance`,
  `scenario`, `production`, `materials`, `suppliers`, `formulation`, `products`,
  `ai`, `knowledge`, `identity`, `tenant`, `audit`, `shared`).

Rules:
- `type:domain` may depend only on `type:domain` and `type:util`.
- `type:application` may depend on `type:domain` and `type:util`.
- `type:infrastructure` may depend on `type:application`, `type:domain`, `type:util`.
- `type:ui` may depend on `type:application`, `type:domain`, `type:util`.

### D-0.2-4 — When `depConstraints` is tightened
In the same task that creates the first library (Task 0.4). Until then, the current
permissive rule is retained.

### D-0.2-5 — Quarantined artifacts
Do not modify, normalize, merge, or clean without a dedicated future task:

| Artifact | Revisit |
|---|---|
| `rag-next-chatbot/package.json`, its lockfile, its `node_modules` | Phase 22 or later |
| `rag-next-chatbot/src/app/` (stale; active tree is `rag-next-chatbot/app/`) | Scoped cleanup task |
| `react-prep/yarn.lock` | Hygiene task |
| `graph.html`, `static/` (untracked) | Undecided; leave alone |
| `packages/` (empty) | No action |

### D-0.2-6 — Nx invocation convention
Use `npx nx …` or `npm exec nx -- …`. Nx is not global and is not aliased in root scripts.

### D-0.2-7 — CI coverage gap
`rag-next-chatbot` lacks `lint`/`test`/`typecheck`/`e2e` targets, so the existing CI
`nx run-many` silently skips those for it. Acknowledged. Fixed only in the phase that
actually works on that app.

### D-0.2-8 — Version pinning
New libraries must match root's pinned `@nx/*` versions exactly where root pins exactly,
and root's ranges where root uses ranges. No new plugin version drift.

### D-0.2-9 — No `paths`, no internal barrels
- `tsconfig.base.json` does not gain a `paths` map.
- Barrel files are permitted at the library public API boundary only. No internal barrels.

### D-0.2-10 — Docs location
`docs/` is introduced in Task 0.3. Phase-0 records live under `docs/phase-0/`.

## 10. Failure scenarios considered
- Task 0.4 creates a library before `libs/*` is added to `workspaces` → package name
  won't resolve at runtime. Mitigation: both happen in the same task (D-0.2-2).
- `depConstraints` tightened before tags exist → spurious failures. Mitigation:
  done together in Task 0.4 (D-0.2-4).
- A future `paths` alias added "for convenience" → violates D-0.2-2/D-0.2-9.
- `rag-next-chatbot` pulled into npm workspaces "to clean up" → violates D-0.2-5.

## 11. System design lesson
Workspace conventions are architecture. Where a library lives, how it resolves, and
what it may depend on is the physical form of the dependency rules the domain model
will later rely on. The absence of a decision is itself a decision.
